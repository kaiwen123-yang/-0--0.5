## 3. 为什么不能只做一次ONNX转换

### 3.1 实际参数对应的容量

按每个参数只存一次计算：

| 表示 | 理想纯权重GB | 理想纯权重GiB |
|---|---:|---:|
| FP32 | 13.414 | 12.493 |
| FP16 / BF16 | 6.707 | 6.246 |
| 全部INT8的理想下限 | 3.353 | 3.123 |
| 全部INT4的理想下限 | 1.677 | 1.562 |

这些是存储计算，不是实测显存。实际还包括部分未量化层、量化scale、视觉／语言激活、KV cache、工作区、运行时和桌面占用。

所以，**原完整模型全部16位权重驻GPU时，单权重就超过6GiB。** 单腕只减少视角输入相关的计算和激活，不自动减少完整语言模型与动作专家参数。显式CPU offload、分组件加载或裁掉经证明无用的参数可能改变驻留量，但都是额外实现，不能由ONNX文件后缀自动得到。

[OpenPI官方README](https://github.com/Physical-Intelligence/openpi/tree/215abfb217dbac7d5f1273282331b9b1866c0479)的常规推理参考为显存>8GB；该参考不是我们3060或自定义压缩实现的实测值。

### 3.2 统一内存解释了“卡小仍可运行”，具体配置仍须保留

现场回执明确写unified memory。在支持超额分配的系统上，这类机制允许GPU使用由运行时管理的主机／设备内存，实际驻留可与“全部权重始终放进显存”的假设不同；代价可能是数据迁移、主机RAM占用和延迟波动。机制见[NVIDIA统一内存说明](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-programming-guide/02-basics/understanding-memory.html)，本机具体能力仍以成功运行环境为准。本次未读取现场分配器、驻留明细或峰值，不能推定具体驻留比例。

restore_concurrent_gb=3限制的是Orbax恢复checkpoint时的并发数据量，有助于降低加载阶段压力；它不表示模型被压缩为3GB，也不表示推理只占3GB。见[Orbax官方参数说明](https://orbax.readthedocs.io/en/stable/api_reference/checkpoint.handlers.html)。实际环境版本和启动变量必须从已运行进程／脚本读取，不照抄最新JAX文档覆盖旧环境。

现阶段最有价值的是补齐实际运行配置、首调用与稳态时延、进程RAM、GPU占用和完整任务耗时；这些数据用于决定是否值得量化，而不是否定本地已运行的回执。

### 3.3 四个概念分别解决什么

| 技术 | 作用 | 对本次6GB问题的意义 |
|---|---|---|
| ONNX | 表达模型计算图与权重的格式 | 单独转换不会自动减小位宽 |
| ONNX Runtime / TensorRT | 执行图、选择和融合算子 | 可能改善延迟，需匹配具体算子、插件和GPU |
| INT8 / INT4量化 | 降低选定权重／运算的精度 | 是减少本地容量的重要候选，需评估动作变化 |
| CPU offload / 分组件驻留 | 改变权重放置位置和加载时序 | 可减少GPU常驻量，可能增加传输及调度成本 |

全参微调和部署量化是不同阶段。训练完成后做量化不等于改成LoRA，也不要求重新采50条或重新做手眼标定。

## 4. 已核实的本地部署技术路线

### 4.1 OpenPI官方转换

当前官方版本215abfb与本项目参考一致，支持JAX和PyTorch及[转换脚本](https://github.com/Physical-Intelligence/openpi/blob/215abfb217dbac7d5f1273282331b9b1866c0479/examples/convert_jax_model_to_pytorch.py)。

必须使用本项目policy_config.model_config(spec)，保留：

```text
pi05=True
discrete_state_input=True
action_dim=32
action_horizon=10
gemma_2b + gemma_300m
```

不能用pi05_droid或pi05_libero代替Piper配置。脚本precision帮助虽然列出float16，当前实际分支只接受float32或bfloat16；不要照帮助给出会报错的float16调用。转换后的导出配置还需明确保留pi05、离散state和本项目处理合同，不能仅依赖原脚本写出的少数字段。

OpenPI官方说明torch.compile下PyTorch与JAX推理速度相近；转换本身不保证更快。转PyTorch主要为后续低位宽／其他后端提供接口。

### 4.2 NVIDIA已经提供实验性π0.5 ONNX/TensorRT参考

[NVIDIA TensorRT-Edge-LLM 0.12.0的π0.5示例](https://nvidia.github.io/TensorRT-Edge-LLM/0.12.0/user_guide/examples/vla/pi05.html)从已转换的PyTorch权重导出visual、prefix、action、cond组件，再由C++运行时执行。固定参考源码513dcd18291e587c80928911a480761352f3c2d8。

现成合同为FP16的pi05_libero、pi05_droid、pi05_aloha；分别具有不同状态维度、视角和horizon。本项目7维状态、单腕和离散state不能假装成LIBERO，仅输出7维／horizon10相同并不足够。需新增Piper合同并使用自身norm。

其独立token embedding文件也不等于CPU常驻：当前pi05Runtime调用的loadSafetensors默认设备为GPU，随后进行设备embedding lookup。拆组件本身不自动解决6GB。x86 GPU支持范围还需结合[该版本支持矩阵](https://nvidia.github.io/TensorRT-Edge-LLM/0.12.0/user_guide/getting_started/support-matrix.html)，未找到本项目在3060 6GB上的实测保证。

### 4.3 本地6GB优先评估W4A16混合精度

[PhyAI作者仓库](https://github.com/mingti-org/phyai)在固定版本bcb6bc312b52cc12ba5fa64201d5a36409e4616c提供π0.5、SM80+的[W4A16配置](https://github.com/mingti-org/phyai/blob/bcb6bc312b52cc12ba5fa64201d5a36409e4616c/examples/pi05/kernel_policies/humming_w4a16.yaml)。它将语言模型／动作专家的attention和MLP线性层做INT4，视觉、embedding和若干输入输出头保留原精度。它是可研究的实现基础，不是已验收的3060部署包。

这条路径可先不经过ONNX，先回答“量化后本机能否装得下、动作是否保持、延迟怎样”。需要处理三个已查明的接口差异：

1. PhyAI的horizon字段为chunk_size，默认50；OpenPI转换目录写action_horizon=10，直接加载可能丢弃未知字段并使用50。必须显式指定chunk_size=10、max_action_dim=32、num_inference_steps=10。
2. 原示例使用随机图／随机状态。实际适配使用已保存的V01真实观测和固定noise，不把示例输出算作本项目验证。
3. 默认后处理只做unnormalize和slice，没有本项目前六轴加回输入state的AbsoluteActions。复用本项目自己的quantile norm、state tokenize、图像mask和输出恢复，确保只加一次。

先核对量化框架的加载时序；若它先把完整16位模型搬上3060再压缩，启动就可能OOM。需要CPU／分层量化加载或在有资源机器预处理的适配，启动峰值与稳态峰值都记录，不能只算最终权重大小。

3060为Ampere，应选择它实际支持的kernel；不能将Blackwell／Thor的FP4性能直接套过来。TensorRT的INT4和ORT的低位宽图均有算子、量化表示和执行后端限制，硬件支持整数格式不等于当前图能自动高效运行。参考：[TensorRT量化](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/inference-library/work-quantized-types.html)、[CUDA能力表](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)。

若后续转TensorRT engine，应针对目标3060及现场运行时构建／匹配，不能默认将D57的Blackwell engine复制到Ampere直接使用；平台、版本和硬件兼容条件见[NVIDIA支持矩阵](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)。

## 8. 3060本地量化／ONNX支线的实施顺序

这条支线可以与现场自主闭环接续并行，但不替换已跑通的原模型环境，也不抢占正在训练的GPU。先以3060本地统一内存结果为功能和延迟参照。

1. **冻结原模型参照。** 使用9999、自己的norm和现有V01 640窗口预测。训练optimizer/train_state留D57；需要迁移的是推理权重、norm、模型配置、tokenizer及前后处理合同。
2. **转换到正确PyTorch模型。** 在有资源的位置完成转换，保持horizon10、离散state、单腕mask和七维还原。先与原JAX在相同真实观测／noise上比较，区别转换偏差与量化偏差。
3. **实施混合W4A16。** 语言／动作专家线性层优先低位宽，视觉与关键小头保留原精度作为初始方案；正确处理加载峰值。RTN不需要额外激活校准；如果换成需要代表样本的PTQ，只从40条train取样，V01继续评估。“量化校准”不是手眼标定。
4. **在3060运行真实观测。** 记录启动和稳态峰值、端到端延迟、每次输出及与原模型的误差。充分显存余量以桌面和现场必要进程的实测占用为依据，不假造统一百分比。
5. **按需要接TensorRT。** 若选NVIDIA导出框架，新增Piper合同和相应低位宽／驻留策略；按3060生成可兼容engine。导出成功、engine能加载、动作与原模型一致、实机能抓放是不同的完成项。
6. **替换同一个策略接口。** 现场采集／发送和日志保留，只把原JAX策略提供者换成候选后端，再用相同任务摆放比较。
